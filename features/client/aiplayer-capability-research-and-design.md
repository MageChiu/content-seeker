# Client 端实现 `aiplayer` 类播放器效果的调研与设计

## 1. 背景与目标

目标问题：

- 如果希望在当前 `client` 内实现接近 `https://github.com/MageChiu/aiplayer` 的效果，即：
  - 站内稳定播放
  - 可下载
  - 最好还能支持边下边播
  - 在多平台客户端内保持较统一体验
- 那么当前项目的架构和语言选择是否会带来明显困难？
- 为什么前几次调试一直达不到预期效果？

本文结论先行：

- 结论一：`Flutter + Dart` 不是“做不到”，但不适合继续用当前这种“页面层直接拼播放、解析、兜底”的方式去逼近 `aiplayer` 的能力。
- 结论二：当前真正的瓶颈不是语言本身，而是 `client` 缺少播放器产品所需的中间层和平台层，包括：
  - 稳定的播放源解析层
  - 下载任务系统
  - 本地缓存与离线索引
  - 后台任务与任务恢复
  - 平台原生能力封装
  - 站点策略变化后的降级与观测能力
- 结论三：如果继续沿着现在的架构做，调试很容易陷入“某个 URL 偶尔能播，但整体产品始终不稳定”的状态。
- 结论四：推荐继续保留 `Flutter` 作为跨平台 UI 和业务编排层，但必须新增“原生能力插件层 + 下载/缓存领域层 + 数据持久化层”，而不是只在 `player_page.dart` 上补逻辑。

## 2. 参考目标：`aiplayer` 在做什么

`aiplayer` 的效果，本质上不是“一个播放器页面”，而是一整套播放器产品能力：

- 基于稳定原生播放内核播放本地文件、在线流媒体
- 能处理网络播放和格式兼容问题
- 能下载或边下边播
- 对复杂来源链接做解析
- 桌面端可接入本地工具链
- 将“播放器”和“下载器”作为核心系统能力，而不是页面附属功能

从产品能力视角看，`aiplayer` 更接近：

- 原生播放引擎 + 下载引擎 + 来源解析 + 本地文件管理 + UI

而当前项目的 `client` 更接近：

- 搜索结果页 + 轻量播放页 + 少量来源解析 + 浏览器兜底

这两者的复杂度不是一个量级。

## 3. 当前 `client` 架构现状

基于现有代码，`client` 当前技术栈和关键实现如下：

- 技术栈：
  - `Flutter`
  - `Dart`
  - `Provider`
  - `media_kit`
  - `webview_all`
- 目标平台：
  - `Android`
  - `iOS`
  - `macOS`
  - `Windows`
- 当前更偏“搜索客户端”，不是完整播放器客户端

### 3.1 关键代码位置

- 应用入口：`client/lib/main.dart`
- 播放页面：`client/lib/features/player/player_page.dart`
- 播放解析总入口：`client/lib/features/player/playback_resolver.dart`
- Bilibili 解析：`client/lib/features/player/bilibili_playback_resolver.dart`
- 桌面端 `yt-dlp` 解析：`client/lib/features/player/desktop_yt_dlp_resolver_io.dart`
- 播放描述模型：`client/lib/models/media_playback.dart`
- 搜索结果模型：`client/lib/models/search_result.dart`
- 配置持久化：`client/lib/features/settings/settings_provider.dart`

### 3.2 当前播放链路

当前播放大致是以下流程：

1. 搜索得到 `SearchResult`
2. 打开 `PlayerPage`
3. 在页面初始化时调用 `PlaybackResolver.resolve`
4. 根据解析结果选择三种模式之一：
   - `nativeStream`
   - `embeddedWeb`
   - `external`
5. 如果是 `nativeStream`，就直接在页面里创建 `media_kit` 的 `Player`
6. 如果是 `embeddedWeb`，就用 `WebView`
7. 如果都不稳定，就让用户跳浏览器

### 3.3 当前已经具备的能力

- 能播放直接媒体 URL，例如：
  - `.mp4`
  - `.m3u8`
  - `.mp3`
  - `.m4a`
- 能对部分来源做轻度解析：
  - Bilibili API 解析
  - 桌面端通过 `yt-dlp` 做解析
- 能给 `media_kit` 传 `httpHeaders`
- 能对 Bilibili 的视频流和音频流做“主视频 + 次音频轨”拼接尝试
- 有基础播放器 UI：
  - 播放暂停
  - 倍速
  - 音量
  - 拖动
  - 全屏
  - 快捷键

### 3.4 当前明显缺失的能力

以下能力几乎还不存在，或还没有独立成稳定模块：

- 下载任务管理
- 下载队列和并发控制
- 后台下载
- 断点续传
- 下载状态持久化
- 文件完整性校验
- 本地媒体库索引
- 离线播放入口
- 缓存清理策略
- “边播边下”的缓存代理层
- 磁力链接 / torrent 引擎
- 原生平台通道
- 统一错误码和可观测性

## 4. 为什么当前架构很难达到 `aiplayer` 的效果

这部分是本次调研最核心的结论。

### 4.1 当前 `client` 的播放器能力仍停留在“页面能力”

现在的播放器是以 `PlayerPage` 为中心来组织的：

- 页面负责解析
- 页面负责创建播放器实例
- 页面负责处理错误
- 页面负责部分平台特性
- 页面负责某些恢复逻辑

这会导致几个直接问题：

- 播放状态无法独立于页面生命周期存在
- 下载任务无法和页面解耦
- 后台任务没法自然接入
- 播放失败后的重试、切源、降级逻辑会越来越散
- 一旦引入离线缓存，页面层会迅速膨胀

换句话说，现在的代码结构适合“打开一个结果试着播放”，不适合“做一个完整播放器系统”。

### 4.2 解析能力和播放能力耦合过紧

现在的播放成功高度依赖来源解析是否刚好返回一个可播放 URL。

问题在于：

- 视频网站链接并不是稳定媒体地址
- 网站策略、签名、鉴权、分流规则常变
- 有些来源是 DASH，需要音视频分离处理
- 有些来源带有严格 `Referer` / `User-Agent` / cookie 要求
- 有些来源只能通过本地工具链或网页提取

当前项目的解析结果主要输出为：

- 一个主 URL
- 可选一个次音频 URL
- 若干请求头

这对“能播一下”足够，但对“稳定播放器产品”不够，因为缺少：

- 来源能力识别
- URL 生命周期管理
- 解析结果缓存
- 解析失败回退策略
- 多方案优选
- 重新签名 / 刷新机制

### 4.3 缺少下载领域模型，导致“播放”和“下载”不是同一套系统

`aiplayer` 这类产品的关键，不只是能播放，还要能下载或边下边播。

当前项目没有下载领域模型，例如：

- `DownloadTask`
- `DownloadItem`
- `DownloadSegment`
- `DownloadStatus`
- `OfflineMedia`
- `StoragePolicy`
- `CacheEntry`

缺少这些抽象，意味着系统里根本没有“下载子系统”，只有“播放页面”。

这就是前几次调试容易失败的根源之一：

- 你在调的是播放页面
- 目标却是播放器产品

两者层级不一致。

### 4.4 缺少后台任务与持久化

只要目标里包含“下载”，就绕不开：

- 应用退后台是否继续
- 进程被杀后是否恢复
- 任务状态是否持久化
- 下载到一半能否暂停 / 恢复
- 大文件是否支持断点续传

当前 `client` 的持久化主要是设置项，使用的是 `flutter_secure_storage`，并不适合承担下载索引和媒体库索引职责。

缺少的数据层包括：

- 普通数据库
- 本地文件路径索引
- 下载记录表
- 缓存占用统计
- 任务恢复逻辑

### 4.5 当前平台层几乎是空的

`client` 的平台代码目前基本还是 Flutter 默认壳：

- `macos/Runner/AppDelegate.swift`
- `windows/runner/main.cpp`

这说明当前客户端还没有真正建立播放器产品常见的平台能力层，例如：

- 原生下载服务
- 原生通知
- 原生文件选取与沙盒策略处理
- 原生播放器高级选项
- 原生 torrent / FFmpeg / 辅助工具桥接

如果没有这一层，跨平台播放器越往后做，越容易变成：

- Dart 层想做很多事
- 但真正需要的平台能力没有出口

### 4.6 来源复杂度被低估了

从当前代码看，已经出现明显信号：

- Bilibili 需要单独解析器
- iOS 与非 iOS 的解析策略不同
- 桌面端还要靠 `yt-dlp`
- 还加入了大量调试打点

这说明问题不是“某个 API 没调通”，而是来源本身就有高复杂性：

- 页面 URL 不等于媒体 URL
- 同一来源在不同平台表现不同
- 某些音视频轨需要手工组合
- 某些 URL 在一段时间后会过期
- 某些来源依赖 cookie

因此，继续只在当前页面层和 resolver 上迭代，会进入高维护成本区。

## 5. 语言与技术选型是否构成根本障碍

结论：不是根本障碍，但会决定系统该如何分层。

### 5.1 `Flutter + Dart` 适合做什么

适合：

- 跨平台 UI
- 搜索和内容浏览体验
- 统一状态管理
- 播放控制层
- 任务列表、下载管理界面
- 一部分业务编排

不适合单独承担的部分：

- 重度来源解析工具链
- torrent 引擎
- 大文件后台下载内核
- 高稳定度边下边播代理
- 平台级通知与恢复
- 某些深度播放器能力

所以正确判断不是：

- “Flutter 能不能做播放器？”

而是：

- “Flutter 该做播放器系统的哪一层？”

### 5.2 当前语言不是问题，当前分层才是问题

如果继续坚持：

- 不引入原生插件
- 不引入独立下载层
- 不引入数据库
- 不引入平台服务
- 不引入缓存代理

那么即便换语言，也依然会难。

反过来，如果采用：

- `Flutter` 做 UI 和业务层
- 原生或 FFI 插件做底层能力
- 独立下载与缓存模块做核心系统层

那就完全有机会逐步逼近 `aiplayer` 的效果。

## 6. 对当前方案的难度评估

### 6.1 仅实现“稳定播放”的难度

难度：中等偏高

原因：

- 已经有 `media_kit`
- 已经有基础播放页面
- 已经有少量 resolver

但问题是：

- 站点来源复杂
- 解析不稳定
- 平台差异大
- 页面层承担太多职责

如果目标只是：

- 播放直接媒体 URL
- 支持少数来源
- 失败时能优雅降级

那么是可做的。

### 6.2 实现“稳定下载”的难度

难度：高

原因：

- 当前没有下载子系统
- 当前没有后台任务体系
- 当前没有下载状态持久化
- 当前没有离线媒体库
- 当前没有路径和存储策略设计

这意味着下载不是“加一个按钮”，而是新增一整层系统。

### 6.3 实现“边下边播”的难度

难度：高到很高

原因：

- 需要缓存代理或分片下载层
- 需要播放器支持本地代理地址或可增量可读文件
- 需要 seek 时的优先级分片调度
- 需要缓存命中和缺块等待逻辑
- 需要更好的磁盘管理

这部分的复杂度通常显著高于“普通下载”。

### 6.4 实现“磁力链接边下边播”的难度

难度：很高

原因：

- 需要 torrent 引擎
- 需要文件选择和顺序下载策略
- 需要 tracker / peer / piece 管理
- 需要平台打包、签名、权限、商店策略评估
- 移动端资源消耗和后台限制更严格

这类能力如果要做，建议放到桌面优先，不建议一开始就做全平台。

## 7. 为什么之前几次调试都很难达到效果

结合当前代码形态，可以推断之前调试难以成功的原因主要有六类。

### 7.1 目标过大，但落点过浅

目标是：

- 播放器产品能力

实际调试落点是：

- 某个页面
- 某个 resolver
- 某个 URL

这会出现典型错位：

- 某次链接能播，不代表整体可用
- 某次解析成功，不代表产品可交付

### 7.2 把“解析问题”误当成“播放器问题”

很多播放失败表面看是播放器打不开，实际上常见根因是：

- URL 不是稳定媒体地址
- 缺请求头
- 缺 cookie
- 音视频分流没处理好
- 链接已过期
- 平台端底层对该流支持不好

如果没有把“来源解析层”独立出来，问题就会反复表现成“播放器不稳定”。

### 7.3 缺少系统化的失败恢复机制

当前缺少标准化回退链路，例如：

1. 直连 URL
2. 原生 resolver
3. 桌面本地解析
4. WebView
5. 浏览器打开

虽然代码里有部分这种趋势，但还没有抽象成清晰的策略系统，因此：

- 调试常常依赖人工试错
- 成功经验难沉淀
- 失败后的可解释性不够

### 7.4 页面层难以容纳持续增长的复杂度

随着功能增加，页面里已经出现：

- debug event 上报
- 多类播放器状态
- 多种播放模式
- 次音频轨处理
- 全屏状态
- WebView 状态

这说明页面层已经开始承担基础设施职责。继续堆功能会显著降低可维护性。

### 7.5 没有下载链路，无法闭环验证“播放 + 下载”

用户要的是：

- 能播放
- 能下载

但当前只有前半段的雏形，没有后半段体系，因此每次调试实际上都只是在验证“能否临时播放”，自然无法接近最终目标。

### 7.6 缺少“平台差异优先级”策略

例如：

- 桌面端可以更激进地使用本地工具链
- iOS 需要更保守的方案
- Android 对后台下载和通知有额外要求
- Windows / macOS 更适合先做本地下载和离线库

如果所有平台都试图走同一条最复杂路径，成功率会很低。

## 8. 推荐的总体设计原则

推荐继续基于当前仓库演进，而不是立即重写。

核心原则：

- 保留 `Flutter` 作为跨平台 UI 层
- 把“播放、下载、缓存、平台能力”从页面层剥离
- 桌面优先完成高级能力
- 移动端优先完成合规的 HTTP 播放与下载
- 将复杂来源支持做成分级能力，不要求所有平台同时等价

## 9. 推荐目标架构

建议把 `client` 从“页面式播放器”升级成“分层播放器客户端”。

### 9.1 建议分层

#### A. Presentation Layer

职责：

- 搜索页
- 播放页
- 下载管理页
- 离线库页
- 设置页

特点：

- 不直接做复杂下载和解析
- 只消费 service / controller 暴露出的状态

#### B. Application Layer

职责：

- `PlaybackCoordinator`
- `DownloadCoordinator`
- `OfflineLibraryCoordinator`
- `ResolverOrchestrator`

特点：

- 负责流程编排
- 负责状态聚合
- 不直接操作平台 API

#### C. Domain Layer

职责：

- 播放会话模型
- 下载任务模型
- 缓存策略
- 来源能力定义
- 错误模型

核心实体建议：

- `PlayableSource`
- `ResolvedMedia`
- `PlaybackSession`
- `DownloadTaskEntity`
- `OfflineAsset`
- `CacheEntry`
- `SourceCapability`

#### D. Infrastructure Layer

职责：

- HTTP 下载实现
- 本地数据库
- 文件系统管理
- 本地代理缓存
- 来源解析实现
- 平台桥接

#### E. Native Capability Layer

职责：

- 平台下载服务
- 平台通知
- 系统播放器增强能力
- 可选的 torrent / ffmpeg / 本地工具桥接

### 9.2 建议模块拆分

建议在 `client/lib/features` 之外，再逐步引入更稳定的模块边界，例如：

- `client/lib/app/playback/`
- `client/lib/app/download/`
- `client/lib/app/offline/`
- `client/lib/domain/media/`
- `client/lib/domain/download/`
- `client/lib/infra/resolver/`
- `client/lib/infra/storage/`
- `client/lib/infra/download/`
- `client/lib/platform/`

## 10. 播放系统设计建议

### 10.1 不再让页面直接拥有复杂播放逻辑

建议新增：

- `PlaybackCoordinator`
- `PlaybackSessionController`
- `PlayerAdapter`

由它们负责：

- 解析结果选择
- 建立播放会话
- 失败重试
- 切换备选源
- 恢复上次进度
- 对 UI 暴露统一状态

页面只负责：

- 展示播放器
- 触发播放控制操作
- 展示错误和状态

### 10.2 统一播放源模型

当前 `PlaybackDescriptor` 太轻，建议升级为更完整的模型，例如：

```dart
class ResolvedMedia {
  final String sourceId;
  final ResolvedMediaKind kind;
  final Uri primaryUri;
  final Uri? secondaryAudioUri;
  final Uri? subtitleUri;
  final Map<String, String> headers;
  final Duration? expiresAt;
  final List<FallbackCandidate> fallbacks;
  final SourcePolicy policy;
  final bool supportsDownload;
  final bool supportsOffline;
}
```

建议补充的信息：

- 是否允许下载
- 过期时间
- 备选源列表
- 是否需要刷新签名
- 是否允许后台播放
- 是否允许离线缓存

### 10.3 建立 resolver 策略链

建议把 resolver 从“按 if/else 返回一个结果”升级为“策略链”：

1. 直接媒体 URL resolver
2. 站点 API resolver
3. 平台本地工具 resolver
4. Web embed resolver
5. 外部打开 resolver

并对每个来源记录：

- 支持平台
- 成功率
- 是否可下载
- 是否需要鉴权
- 失败原因分类

## 11. 下载系统设计建议

### 11.1 下载必须单独成系统

建议引入独立下载领域，而不是在播放器页里附加“下载按钮”。

最低需要的对象：

- `DownloadTaskEntity`
- `DownloadRequest`
- `DownloadProgress`
- `DownloadRepository`
- `DownloadScheduler`
- `DownloadStorageManager`

### 11.2 下载任务状态机

建议的最小状态机：

- `queued`
- `resolving`
- `running`
- `paused`
- `completed`
- `failed`
- `canceled`

建议额外记录：

- 总大小
- 已下载字节数
- 当前速度
- 重试次数
- 文件保存路径
- 来源类型
- 最后错误

### 11.3 下载能力分层

建议分三档，不要一步到位：

#### 第一档：直接文件下载

支持：

- 直链 `mp4/mp3/m4a`
- 断点续传
- 暂停恢复
- 后台下载

这是最容易先落地的一层。

#### 第二档：流媒体离线化

支持：

- `m3u8` / DASH 的离线保存
- 分片索引
- 合并或离线清单维护

这层明显比普通文件下载复杂。

#### 第三档：边下边播 / 磁力

支持：

- 本地代理边下边播
- torrent 引擎
- 文件选择
- 分片优先级调度

建议最后做。

### 11.4 存储设计

建议目录模型：

- `appSupport/media/cache/`
- `appSupport/media/downloads/`
- `appSupport/media/offline/`
- `appSupport/media/temp/`

建议数据库表：

- `downloads`
- `offline_assets`
- `playback_history`
- `resolver_cache`
- `cache_entries`

## 12. 边下边播设计建议

如果目标包含“像 `aiplayer` 一样边播边下”，推荐采用“本地缓存代理”思路，而不是让播放器直接读取未完成文件。

### 12.1 推荐方案

核心思路：

1. 用户点击播放
2. 下载管理器按块下载远端资源
3. 本地代理服务暴露一个本地 URL
4. 播放器读取本地代理 URL
5. 代理命中已缓存块直接返回，缺块则等待下载完成

优势：

- 播放器感知简单
- 可以做 seek 优先级
- 可以复用缓存
- 更容易支撑离线化

问题：

- 实现复杂度高
- 各平台网络权限和本地回环地址要处理
- 清理策略和一致性要做得足够好

### 12.2 不建议的简化方案

不建议一开始采用：

- 边下载到单文件，边让播放器直接打开这个文件

原因：

- 不同播放器对增长中文件支持不一致
- seek 和随机访问体验通常不好
- 容易产生平台差异 bug

## 13. 平台差异建议

### 13.1 桌面端

最适合优先实现高级能力：

- 本地工具链集成
- 下载与离线文件管理
- 更强的 resolver
- 更复杂的缓存策略
- 可选 torrent 能力

建议桌面优先支持：

- 稳定播放
- 直接下载
- 简单边下边播

### 13.2 iOS

建议保守设计：

- 优先做直接播放
- 优先做合规 HTTP 下载
- 减少依赖外部可执行文件
- 谨慎处理第三方平台内容下载能力

建议 iOS 初期不承诺：

- 桌面同级别站点解析能力
- torrent
- 高自由度本地工具链

### 13.3 Android

可比 iOS 更积极，但仍建议分阶段：

- 先做直接下载和后台任务
- 再考虑缓存代理
- 最后再评估 torrent

### 13.4 Windows / macOS

建议作为第一优先平台：

- 最容易验证完整播放器能力
- 最适合先跑通下载与离线化闭环
- 更适合引入本地增强工具

## 14. 推荐实施路线

### 阶段 0：停止继续在页面层硬补

目标：

- 不再把复杂能力继续叠加到 `player_page.dart`

动作：

- 抽离 `PlaybackCoordinator`
- 抽离 resolver 策略接口
- 定义下载和离线的领域模型

### 阶段 1：先把“稳定播放”做扎实

目标：

- 桌面 + 移动端都能稳定播放直链和少数重点来源

范围：

- 统一播放状态模型
- resolver 策略链
- 平台差异化回退
- 播放错误码和日志

验收标准：

- 直链媒体稳定播放
- Bilibili / YouTube 至少一种稳定降级路径
- 播放失败能说明原因并自动回退

### 阶段 2：新增“普通下载”闭环

目标：

- 支持直链资源下载到本地并离线播放

范围：

- 下载列表页
- 下载状态持久化
- 文件存储策略
- 离线资产索引

验收标准：

- 下载可暂停 / 恢复
- 退出应用后能恢复状态
- 下载完成后可在离线库播放

### 阶段 3：新增“缓存代理边播边下”

目标：

- 对 HTTP 资源支持流式缓存播放

范围：

- 块级缓存
- 本地代理
- seek 优先块下载
- 缓存命中复用

验收标准：

- 开播无需先下完整文件
- seek 后能快速补齐目标区域
- 缓存文件可被后续复用

### 阶段 4：桌面端增强能力

目标：

- 让桌面端更接近 `aiplayer`

范围：

- 更强 resolver
- 可选本地工具链
- 高级离线化
- 可选 torrent

验收标准：

- 桌面端形成“搜索 -> 播放 -> 下载 -> 离线播放”的完整闭环

## 15. 推荐的近期落地方案

如果希望控制风险，建议选择以下路线。

### 15.1 推荐路线：保留 Flutter，重构 client 分层

这是最推荐的方案。

理由：

- 保留现有多平台基础
- 保留现有搜索和 UI 代码
- 成本明显低于重写
- 适合分阶段推进

但前提是必须接受：

- 要增加平台能力层
- 要增加下载系统
- 要增加数据库和文件系统抽象
- 要允许桌面与移动的能力不完全对齐

### 15.2 不推荐路线：继续只在现有页面上补功能

原因：

- 复杂度会持续堆到 `player_page.dart`
- 新增下载后代码会迅速失控
- 问题定位会越来越困难
- 很难形成稳定产品

### 15.3 条件性路线：桌面端先做强，移动端保守跟进

这是非常现实的折中方案。

策略：

- `macOS` / `Windows` 优先实现高级播放与下载
- `iOS` / `Android` 先实现稳定播放与普通下载
- 复杂来源和高级离线化先在桌面验证

这能显著提高交付概率。

## 16. 预估风险

### 16.1 技术风险

- 站点解析规则变化快
- 不同平台底层播放器行为不一致
- 边下边播对缓存一致性要求高
- 大文件下载对后台机制依赖强

### 16.2 产品风险

- 用户预期是“像桌面原生播放器一样稳定”
- 但移动端体验天然受平台限制
- 若不做分平台能力说明，容易产生预期落差

### 16.3 工程风险

- 现有代码尚未形成播放器域模型
- 一旦边改边加功能，返工概率高
- 如果没有阶段目标，会长期卡在“偶发可用”

## 17. 最终判断

### 17.1 能不能做

能做。

但前提不是“继续调当前页面直到成功”，而是：

- 先承认当前 `client` 还不是播放器架构
- 再把播放器系统真正建出来

### 17.2 难点到底在语言还是架构

主要在架构，不在语言。

更准确地说：

- `Flutter/Dart` 适合作为上层
- 不适合单独扛起全部播放器底层能力
- 需要原生能力和基础设施模块补位

### 17.3 当前是否实现起来比较困难

如果以当前架构直接实现“接近 `aiplayer` 的播放 + 下载 + 边下边播效果”，答案是：

- 是，比较困难

困难的真正原因是：

- 当前 `client` 缺少播放器产品所需的系统层
- 不是因为 `Flutter` 天生不能做

## 18. 建议的明确决策

建议现在做以下决策：

1. 决定采用“Flutter 保留 + 分层重构 + 平台能力补齐”的路线
2. 明确桌面优先，移动端分阶段跟进
3. 第一阶段只承诺“稳定播放 + 普通下载”，不同时承诺 torrent 和全量边下边播
4. 把后续开发目标从“修某个播放 bug”改成“建设播放系统、下载系统和离线系统”

## 19. 建议下一步任务拆分

建议按以下顺序开工：

1. 设计新的播放领域模型与下载领域模型
2. 抽离 `PlaybackCoordinator` 和 resolver 策略层
3. 新建下载模块和本地数据库
4. 先实现桌面端的直链下载与离线播放
5. 再实现移动端的下载闭环
6. 最后评估边下边播与 torrent

---

## 附：一句话结论

如果目标是做出接近 `aiplayer` 的效果，当前 `client` 不是语言选错了，而是架构还停留在“可试播的搜索客户端”阶段；要达到“可播放 + 可下载 + 可演进”的播放器产品水位，必须把下载、缓存、平台能力和来源解析从页面层里独立出来。
