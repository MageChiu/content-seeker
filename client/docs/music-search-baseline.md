# 音乐搜索基线

## 范围

- 仅针对 `client/` 当前本地音乐搜索能力。
- 不包含服务端远程聚合能力。

## 当前参与音乐搜索的主要本地源

- `itunes`
- `deezer`
- `jamendo`
- `internet_archive`

## 当前链路

- 搜索页输入关键词
- `SearchProvider` 接收查询并做本地 LLM 改写
- 按 `supportsAudio` 和 `isLocalSourceReady` 筛选本地源
- 各源内部自行改写 query 并请求第三方接口
- 聚合结果后在 `SearchProvider` 排序
- 搜索页展示结果并进入播放器

## 主要瓶颈

### 1. query 改写过轻

- 复杂输入如 `歌手 - 歌名`、`歌名 live`、`歌名 feat. xxx` 处理不充分。
- 对不同音乐源没有形成足够稳健的候选 query 组合。

### 2. 去重过粗

- 旧逻辑主要按 `source + id` 去重。
- 同一首歌跨源返回时容易在前几位重复出现。

### 3. 排序缺少 query 感知

- 原有排序更偏通用媒体结果评分。
- 对“标题是否真的命中歌名”“歌手是否匹配”考虑不够。

### 4. 现有源能力没有完全用满

- `iTunes` 只做单地区、单轮查询，且对 preview 依赖较强。
- `Jamendo` 只用 `namesearch`，模糊召回不足。
- `Internet Archive` 噪声较多，容易混入播客或非音乐音频。

### 5. 目录声明与实际能力存在偏差

- `youtube` 在目录层被标为支持音频，但本地实现只返回视频结果。

## 本轮优化目标

- 强化音乐 query 改写
- 引入 query 感知排序
- 改为按歌曲特征去重
- 优化现有四个音频源
- 新增一个适合纯 `client` 接入的音乐源

## 首个新增源选择

- 本轮优先选择 `Audius`

原因：

- 有公开音乐搜索接口
- 有可直接流式播放的音频接口
- 适合客户端直连
- 比需要更强凭证保护的方案更符合当前边界
